# Scratch AI detector
Detects AI-generated Scratch projects (Work in progress)

## Usage
Just run main.py however you like, you don't need to install anything else other than Python.

When running the program you'll get prompted to select a project. The numbered options are selected from the samples directory. You can either:
* Put your `.sb3` file there
* Enter a project ID and wait for the `project.json` file to download. There's no error handling yet; if the project is unshared, the program will crash.

All outputs are directed to `logs.md` unless specified otherwise.

### Flags
* `--output-logs`: Print the test logs to the console instead of to `logs.md`.
* `--no-log-sections`: Remove collapsible log sections in `logs.md`. Has no effect hen `--output-logs` is enabled.
* `--min-sequence`: The minimum block count of a detectable sequence. Defaults to `5`.

# Detection methods

## Test Categorization

| Test | Effectiveness | False positives |
|--|--|--|
| Variable IDs | Strong | Low |
| Coordinates | Moderate | Moderate |
| Repetition | Moderate | Moderate |
| Default input values | Weak to moderate | Moderate |
| Variable naming convention | Weak | Moderate |

### Conclusion

* Variable IDs remain the strongest signal because Scratch-generated IDs are hard to fake convincingly without leaving obvious numerical or name-based artifacts.
* Coordinates are moderately useful for spotting templated or grid-like AI layouts, but they are not definitive on their own.
* Repetition is a moderate signal only when it is high-quality, non-boilerplate repetition across scripts or sprites; weak or repetitive boilerplate patterns are filtered out to reduce false positives.


## Variable IDs
Inside of `project.json`, each variable in a Scratch project is stored with a variable ID that holds both the variable name and its value:
```json
{
    "<variable id>": [
        "<variable name>",
        value
    ]
}
```
We explain each parameter in the detection below:

### Scratch generated
Normally, the Scratch editor generates 20 character long string made up from a specific list random characters. It is possible to check if variables were made with the Scratch editor by checking if the variable ID doesn't have any characters not in the list and the variable ID is not 20 characters long.

### Code generated
These are variable IDs that roughly match the variable name. This is checked by removing all symbols in both the variable name and ID and comparing both. This means that for example, "Very! cool_variable58" becomes "verycoolvariable58" for the check. If both match, then it means that it could be possible for the project.json to have been generated by a program other than Scratch, such as one of the many text-to-scratch compilers out there, or AI. It doesn't confirm AI use by itself though.

### Numerically generated
These are simply variable IDs that contain a number. Sometimes you'll find variable IDs that are named v1, v2, v3, etc. or have similar numerical names. These usually show up in AI-generated projects, although not always. It's still plausible for these to have been generated by a program.

### Other
Variables that don't fit any of the previous criteria, or are numerically generated, get added to this counter. This is a pretty strong sign that a project is AI-generated, there's no reason for a human to change the variable ID manually. *Except for minimizers, detection for which will be added soon*.

## Coordinates

In a Scratch project, the coordinates of top-level blocks (blocks with `topLevel: true` or `parent: null`) are mostly random or placed on a grid (with an extension such as **Clean up Blocks +**).

This test checks if there's a grid-like pattern or stacked blocks on one coordinate. An AI-generated Scratch project often has coordinates in top-level blocks such `"150, 100; 0, 10..."` and not `"157, 102; 2, 13..."`

## Repetition
Repeated block patterns are another potential sign of AI generation. In AI-generated projects, the same script structure often appears multiple times even across different sprites, with only minor changes in inputs or references.

That said, even though generated code can be unnaturally uniform, humans also produce duplicate code heavily due to Scratch's limitations. Therefore, the repetition test ignores low-signal patterns such as repeated `procedures_call` chains or initialization-only list/variable updates, because those are often boilerplate and are common in human-made projects.

### Procedure
1. The analyzer identifies repeated sequences and subsequences of blocks. It compares block signatures based on their opcode, fields, mutation, and input layout, allowing structurally equivalent blocks to be grouped even when their underlying block IDs or inputs differ.
2. The analyzer finds matching sequences of at least a specified minimum length, extending matches for as long as subsequent block signatures remain identical. This allows it to identify complete duplicate sequences as well as repeated portions of otherwise different scripts.
3. The analyzer then measures and produces a report based on the following:
    * per-sprite repetition
    * cross-sprite repetition
    * whole-project repetition ratio

### Repetitiveness report
The report includes a short preview such as:

```
motion_movesteps -> motion_turnright -> motion_turnleft
```

and data such as:

```
3x motion_movesteps -> motion_turnright -> motion_turnleft (3 blocks)
```

It also calculates a repetition ratio as follows:
```
                   duplicated blocks in matched patterns
repetition ratio = -------------------------------------
                     total blocks in matched patterns
```

In the current implementation, this is the ratio of duplicated blocks inside the filtered, non-boilerplate repeated sequences that survived the signal check. This makes it stronger and more conservative than dividing by every block in the project.

A high repetition ratio indicates that a project contains substantial amounts of duplicated code, especially when similar patterns repeat in lots of scripts or sprites. However, repetition alone is not definitive evidence of AI generation, and a low ratio **does not mean that the project is not AI-generated**!

## Default input values
This test measures how often a project leaves Scratch default input values untouched. Currently, it is a weak-to-moderate residue signal rather than a definitive indication of AI generation.

### Procedure
1. The analyzer walks every block in every sprite and checks whether its opcode/input pair matches an internal table of known `(opcode, input name) -> default value` pairs.
2. Only literals are considered valid candidates. Reporter inputs, variable references, list references, or menu choice are ignored so they do not distort the results.
3. Input values are unwrapped recursively. This includes nested Scratch input encodings and reporter-wrapped values, so a literal such as `[1, [4, "10"]]` or `[3, "<ref>", [4, "10"]]` is reduced to the scalar value when it actually holds a literal value.
4. Numeric comparisons are done numerically, so values like `"10"`, `10`, and `"10.0"` all count as the same default.
5. The result is reported as `hits/total`: the count of typed inputs still at their default value divided by the count of valid candidate inputs.
6. A sprite or project with fewer than 30 candidate inputs is reported as "too few to read".

### Interpreting results
* Human-made projects usually leave some defaults behind, while generated code often changes them.
* A project with a lot of untouched defaults may look AI-generated, but this is only a weak signal and should be read alongside the other tests.
* Technical projects often have fewer defaults more than simpler ones.
* The test is **best treated as a background clue** rather than a clear indicator of AI generation.

### Limitations
* The implementation intentionally excludes reporter-backed and menu values because they are not true typed literals; a generator can still leave defaults in place on purpose and a human can remove them deliberately.
* Small projects and specialized styles can produce noisy or misleading ratios.

## Variable naming

This test finds how consistently variables and lists are named in a project, using a naming-style classification and Shannon entropy.

### Procedure
1. Each name is classified as one of:
    * `single letter`
    * `lowercase`
    * `uppercase`
    * `words`
    * `dots`
    * `camelCase`
    * `PascalCase`
    * `snake_case`
    * `kebab-case`
    * `SCREAMING_SNAKE_CASE`
    * `SCREAMING-KEBAB-CASE`
    * `Title Case`
    * `other`
2. For each sprite and for the whole project (`(project)`), the report includes:
    * `count`: number of names
    * `entropy`: Shannon entropy of the style distribution, in bits
    * `entropy_norm`: entropy divided by the maximum possible entropy
    * `mode`, `mean`, `stdev`: statistics of the name lengths
    * The count of each naming style (most common first)

### Interpreting results
* `entropy = 0` means every name uses the same style. About 1 bit means two styles used evenly, and 2 bits means about four.
* To compare entropies between projects, use the project's entropies. Per-sprite entropies are noisy, as most sprites have few variables.
* `entropy_norm` is only roughly comparable between projects, because real projects use a handful of styles, not all of them.

### Limitations
* This tool only measures naming consistency, and there are many ways that this can incorrectly determine a project's standing:
    * a careful human can be perfectly consistent when naming
    * a project full of single-letter names is also low-entropy
    * ...
* Naming conventions can change over time.
* Renaming variables can erase the signs about naming consistency.
